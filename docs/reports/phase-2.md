# Phase 2 보고서 — 재고 조건을 잠금 SELECT 의 WHERE 로 (부족 시 락 없이 즉시 거절)

- **브랜치**: `phase-2/precheck-before-lock`
- **상태**: 측정 완료 — 졸업 조건 3/3 충족 (2026-09-04). 해석(섹션 2·3·4) 사용자 작성 중
- **동기 (Phase 1 결과)**: `FOR UPDATE` 로 정합성은 회복(수락 106 = 재고 106, oversold 0)했으나 rps −41% / p95 ×2.7 / med ×5.7. 내부 샘플링에서 DB 세션 15~19개가 30초 내내 행 락 대기, 풀 20/20 포화, 커넥션 대기 스레드 최대 283. 성공 106건은 2.87초에 끝났는데 락 경합이 끝까지 이어진 이유는 **`FOR UPDATE` 가 재고 검사보다 먼저라 거절될 요청도 락을 잡고 나서야 거절**되기 때문. ([phase-1.md](./phase-1.md) 섹션 2·보조 관측)
- **가설**: Phase 1 비용의 대부분은 성공이 아니라 **거절 트래픽의 락 경합**이 만든다. 거절을 락 앞에서 걸러내면 재고 소진 이후 구간의 락 경합이 사라지고 rps·p95 가 Phase 0 근처로 회복된다. 남는 비용은 소진 구간(≈3초)의 직렬화, 즉 락 보유 시간(메커니즘 b)의 몫이다.
- **구현 정책**: 최소 변화 하나 — 잠금 SELECT 의 WHERE 에 재고 조건을 넣는다: `SELECT stock_qty FROM products WHERE id = ? AND stock_qty >= ? FOR UPDATE`. PostgreSQL 의 `FOR UPDATE` 는 조건에 맞아 반환되는 행에만 락을 잡으므로, 재고 부족이면 **락 없이 빈 결과** → 즉시 `InsufficientStockException`; 충분하면 락을 잡고 기존 경로(차감 → 주문 INSERT)로 진입. 락을 기다렸다 깨어난 트랜잭션은 갱신된 행으로 조건이 재평가되므로(READ COMMITTED 재검사) 그사이 재고가 바닥나면 역시 빈 결과. 정합성은 여전히 락이 지킨다. 조회 메서드의 의미가 "재고 조회"에서 "재고가 quantity 이상이면 잠그고 반환, 아니면 null" 로 바뀌므로 시그니처(quantity 인자)와 이름을 그에 맞춘다. 앱 쪽 `if (stock < quantity)` 검사는 WHERE 로 흡수되어 제거 가능. (검토한 대안: 락 없는 일반 SELECT 를 앞에 두는 사전 확인 — 효과는 같으나 성공 경로 왕복이 1회 늘고 검사가 두 곳으로 갈라짐. `NOWAIT`/`SKIP LOCKED` 는 재고가 남아 있어도 락 보유 중이라는 이유로 거절해 flash-sale 의미와 어긋나 제외.)
- **성격**: 메커니즘 (a)(거절 트래픽의 락 경합)만 제거하고 (b)(락 보유 구간 = 트랜잭션 전체)는 그대로 둔 **진단용 중간 단계**. 검증되면 Phase 3 에서 조건부 UPDATE(`UPDATE … WHERE stock_qty >= ?`, 판단과 차감을 한 문장으로) 로 옮기며 (b) 를 잰다 — 이번 형태는 그 다음 걸음과 모양이 거의 같다.

계측을 켤수록 rps 가 내려가고 p95 가 올라간다. 섹션 1 측정 표의 값과 직접 비교하지 않는다.

소진 구간 (실행 ①, 총 요청 61,595건):

- 성공 106건의 `created_at` 은 k6 시간축 0.06~1.49초(**1.43초**)에 있다. 이 구간에 시작한 요청은 **122건(전체의 0.2%)** 이고, 그 요청들의 med / p95 / max 는 35 / 463 / 747ms 다. 0.1초 묶음당 요청 수는 8~12건(부하 정점은 300~400건).
- 전체 p95(61.0ms) 이상인 요청 3,081건 중 이 구간에서 시작한 요청은 **34건**이다. 구간을 빼고 계산하면 p95 60.8ms, rps 2,049(빼기 전 61.0ms, 2,053).
- 비교용: 실행 ②에서 요청이 가장 몰린 1.5초(23.3초부터)에 시작한 요청은 **5,891건**, 전체(64,888건)의 5% 는 3,244건.

부하 정점의 지연 봉우리:

- 두 실행 모두 **19.5~19.7초**에 나타났다 (실행 ① 19.6초 묶음: 384건, med 255ms / p95 376ms · 실행 ② 19.6초 묶음: 204건, med 194ms / p95 344ms). 9월 5일 실행에서는 22.1초·25.0초. p95 150ms 이상인 0.1초 묶음(3초 이후)은 두 실행 모두 6개.
- 늘어난 것은 `http_req_waiting`(요청 전송 후 첫 응답까지): 평소 5~20ms → 봉우리 130~260ms. 새 연결은 0.1초당 0~7개로 봉우리 전후와 같고, `http_req_blocked` 는 0.1초 묶음 평균 최대 1.1ms.
- 행 락 대기: 소진 이후 모든 내부 샘플에서 0.
- GC: 실행 ②의 봉우리(20:33:36.1~36.6) 안에는 GC 가 없다. 앞뒤 멈춤은 3.8ms(35.945), 13.4ms(37.007). 실행 ①의 봉우리에는 동시 마킹 주기(250ms, 멈춤 구간은 Remark 10.6ms)가 겹쳤다. 9월 5일 봉우리 두 곳의 GC 멈춤은 4~6ms 이고 동시 마킹 주기는 없다.
- PostgreSQL 체크포인트: 20:25:36, 20:30:36, 20:35:36 시작. 봉우리 시각과 겹치지 않는다.
- CPU (8코어): 실행 ①은 14~28초 평균 합계 7.37, 봉우리 순간 최대 8.64. 실행 ②는 평균 6.77, 봉우리 순간 5.7~7.6. 내부 샘플을 빼자 "그 외" 몫이 평균 1.23 → 0.50 으로 줄었다.
- JFR (실행 ②): 봉우리 전후 약 0.6초 동안 앱 실행 샘플이 0.1초당 9~10회 → 3~5회로 줄었다(0 은 아님). 같은 구간 가상 스레드 캐리어(`ForkJoinPool` 워커)는 작업 대기로 파킹, 20ms 이상 이벤트 중 역최적화·가상 스레드 고정은 없음. JFR 기본 설정은 20ms 미만 대기를 기록하지 않는다.
- 앱 로그: 경고·예외 없음 (HikariCP 시계 도약·스레드 기아 경고 포함).
- 내부 샘플(실행 ①): 16.5~28.4초의 샘플 5개에서 풀 active 19~20, pending 최대 57. 9월 4일 실행은 19.2초 한 샘플만 20/20.
