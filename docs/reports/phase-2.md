# Phase 2 보고서 — 락 없는 사전 확인 후 FOR UPDATE

- **브랜치**: `phase-2/precheck-before-lock`
- **상태**: 진행 중 (구현 전)
- **동기 (Phase 1 결과)**: `FOR UPDATE` 로 정합성은 회복(수락 106 = 재고 106, oversold 0)했으나 rps −41% / p95 ×2.7 / med ×5.7. 내부 샘플링에서 DB 세션 15~19개가 30초 내내 행 락 대기, 풀 20/20 포화, 커넥션 대기 스레드 최대 283. 성공 106건은 2.87초에 끝났는데 락 경합이 끝까지 이어진 이유는 **`FOR UPDATE` 가 재고 검사보다 먼저라 거절될 요청도 락을 잡고 나서야 거절**되기 때문. ([phase-1.md](./phase-1.md) 섹션 2·보조 관측)
- **가설**: Phase 1 비용의 대부분은 성공이 아니라 **거절 트래픽의 락 경합**이 만든다. 거절을 락 앞에서 걸러내면 재고 소진 이후 구간의 락 경합이 사라지고 rps·p95 가 Phase 0 근처로 회복된다. 남는 비용은 소진 구간(≈3초)의 직렬화, 즉 락 보유 시간(메커니즘 b)의 몫이다.
- **구현 정책**: 최소 변화 하나 — `PlaceOrderService.place()` 에서 `FOR UPDATE` 진입 **전에** 락 없는 일반 SELECT 로 재고를 확인하고, 부족하면 즉시 `InsufficientStockException`. 여유가 있을 때만 기존 경로(`FOR UPDATE` → 검사 → 차감)로 진입. 정합성은 여전히 락 뒤의 검사가 지킨다(사전 확인은 "빨리 거절"용이라 사전 확인과 락 사이의 틈은 무해). Phase 1 의 `findStock()` 잠금은 그대로 둔다.
- **성격**: 운영 최종형이 아니라 **진단용 중간 단계** — 같은 값을 두 번 읽는 군더더기를 감수하고 "거절 트래픽 가설"을 단독 검증한다. 검증되면 Phase 3 에서 조건부 UPDATE(판단과 차감을 한 문장으로) 로 옮기며 메커니즘 (b) 를 잰다.

## 졸업 조건 (시작 전 선언)

Phase 0·1 과 **같은 부하·같은 초기 재고**(`RESET_STOCK=106`, `load-test/flash-sale.js` 30s). 세 신호 모두 충족해야 졸업 (정합성 유지 + 가설 검증 + 비용 회복).

| # | 신호 | 측정 방법 | 충족 기준 |
|---|---|---|---|
| 1 | **정합성 유지** | `measure.sh` 출력 `oversold`, `final_stock_qty` | `oversold ≤ 0` **그리고** `stock_qty ≥ 0` (Phase 1 과 동일) |
| 2 | **소진 후 락 경합 소멸** (가설 직접 검증) | `sample-internals.sh` 의 `db_lock_wait` 열, 재고 소진 이후 샘플 | 소진 이후 샘플에서 `db_lock_wait` 가 지속적으로 0~1 (Phase 1: 15~19 지속) |
| 3 | **비용 회복** | k6 요약 rps / p95 | rps ≥ **1,500** (Phase 0 기준선 ≈1,800~1,900 의 80%) **그리고** p95 ≤ **150ms** (기준선 ≈93~104ms 의 1.5배) — _수치는 제안값, 구현 전 사용자가 근거와 함께 확정_ |

Phase 0 기준선은 두 실행(1,816 rps / p95 104ms, 대조군 1,927 / 93ms), Phase 1 은 두 실행(1,077 / 279ms, 1,152 / 268ms).

### 측정 절차

```
load-test/restart-app.sh
load-test/sample-internals.sh 36 load-test/out/internals-phase2.csv &
RESET_STOCK=106 load-test/measure.sh
wait
```
