# Phase 3 보고서 — 재고 확인과 차감을 조건부 UPDATE 한 문장으로

- **브랜치**: `phase-3/conditional-update`
- **상태**: 시작 — 기준선과 Phase 0 코드 대조 측정 완료 (2026-09-13). 가설·졸업 조건 기준값은 사용자 확정 전, 구현 전
- **동기 (Phase 2 결과)**: 재고 조건을 잠금 SELECT 의 WHERE 로 옮기자 소진 이후의 락 경합이 사라지고 rps·p95 가 Phase 0 수준으로 돌아왔다(2,196 rps / p95 39ms). 남은 비용은 재고가 남아 있는 동안 주문들이 행 락을 차례로 기다리는 시간이다. 재고 106개 시나리오에서는 이 구간이 1.43~1.58초, 전체 요청의 0.2% 라 30초 전체 수치에 드러나지 않았다. 재고를 늘려 판매가 부하 정점까지 이어지게 하면 이 비용이 전체 수치를 지배한다(아래 기준선). ([phase-2.md](./phase-2.md) 보조 관측 — 시간축 계측)
- **변경 (최소 변화 하나)**: 잠금 SELECT(`… AND stock_qty >= ? FOR UPDATE`) 와 이어지는 차감 UPDATE 두 문장을, 조건을 건 UPDATE 한 문장(`UPDATE … SET stock_qty = stock_qty - ? WHERE id = ? AND stock_qty >= ?`)으로 합친다. 반영된 행 수가 1 이면 성공, 0 이면 재고 부족. 주문 INSERT 와 트랜잭션 경계는 그대로 둔다.

## 측정 시나리오

부하는 Phase 0~2 와 같다(`load-test/flash-sale.js`, 30초, VU 0→100→500→0). 초기 재고만 두 가지로 잰다.

| 시나리오 | 초기 재고 | 목적 |
|---|---|---|
| A. 기존 | `RESET_STOCK=106` | 이전 phase 와 이어지는 비교 (부하 시작 직후 소진) |
| B. 정점 소진 | `RESET_STOCK=3000` | 판매가 부하 정점까지 이어져 락 대기 비용이 전체 수치에 드러나는 조건 |

재고 3,000 은 탐색 실행으로 정했다: 재고 1,500 은 판매가 14.04초에 끝나 VU 정점(20~25초)을 비껴갔고, 3,000 은 23.66~24.85초 동안 이어졌다.

### 측정 절차

```
load-test/restart-app.sh
RESET_STOCK=106 load-test/measure.sh           # 예열 — 결과는 버린다
RESET_STOCK=106 load-test/measure.sh           # 시나리오 A
# 시나리오 B (2회) — 매 실행 전에 VACUUM (ANALYZE) products
RESET_STOCK=3000 load-test/measure.sh
```

판매 지속 시간: 실행 직전 시각을 기록해 두고 `orders.created_at` 의 첫 주문~마지막 주문 차이로 잰다. 시나리오 B 는 rps 가 30초 안에 소진했는지에 크게 좌우되므로 비교의 주 지표는 **초당 판매 건수**다(아래 대조 참조).

재고 3,000 한 번 판매로 `products` 에 죽은 행 버전이 800개 넘게 쌓인다. VACUUM 없이 이어 돌린 실행에서 초당 판매가 92건까지 떨어진 적이 있다(원인이 죽은 행 버전인지는 가리지 못했다). 실행마다 시작 상태를 같게 하려고 매 실행 전에 VACUUM 을 한다. 아래 기준선 ①·② 는 VACUUM 없이 잰 값이다.

### 대조 — 재고를 늘린 것만으로 생긴 비용과 락 대기 비용 가르기 (2026-09-13)

재고를 106 → 3,000 으로 늘리면 락을 차례로 기다리는 시간만 늘어나는 것이 아니라 성공 주문(주문 INSERT·커밋)도 약 28배가 된다. 둘을 가르려고 잠금 SELECT 가 없는 Phase 0 코드(`phase-0/baseline-no-locking`, 락 없는 SELECT 로 재고를 읽고 조건 없는 UPDATE 로 차감)로 같은 시나리오를 쟀다. Phase 0 코드도 UPDATE 순간부터 커밋까지는 행 락을 잡는다(UPDATE → 주문 INSERT → 커밋) — 이번 변경 뒤의 락 모양과 같다.

두 jar 의 재고 저장소 클래스를 `javap` 로 확인했다: Phase 2 기준선 jar 에는 `STOCK_QTY.ge` 와 `forUpdate` 호출이 있고, Phase 0 jar 에는 둘 다 없다.

| 재고 3,000 | 실행 전 `VACUUM products` | 초당 판매 | rps | med / p90 / p95 / max | 판매 / 부하 후 stock |

함께 뽑은 사실:

- 같은 절차(실행 전 VACUUM)에서 초당 판매는 Phase 0 코드 129.0~133.3건, Phase 2 코드 119.7~127.8건이다. 같은 코드끼리의 실행 간 차이는 약 3~7%.
- 이 시나리오의 rps 는 30초 안에 소진했는지에 크게 좌우된다. 소진 뒤 남은 시간에는 빠른 409 거절이 이어져 rps 가 올라가고, 소진하지 못하면(Phase 0 ②) 모든 요청이 락을 기다려 rps 92, med 2,611ms 가 된다.
- 재고 3,000 한 번 판매 뒤 `products` 의 죽은 행 버전은 823. Phase 0 ②(92건/초) 직전의 죽은 행 수는 기록하지 못했고, 같은 실행 도중 21:26:09 에 자동 VACUUM 이 돌았다.
- 실행 사이 트랜잭션을 연 채 남은 세션 없음, 앱 로그 경고·예외 없음.
- VACUUM 을 한 실행이 더 빠른 것은 앱 예열이 더 된 뒤의 실행이라는 점과 섞여 있다.
