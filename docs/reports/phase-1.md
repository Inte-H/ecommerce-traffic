# Phase 1 보고서 — SELECT … FOR UPDATE (비관적 행 잠금)

- **브랜치**: `phase-1/select-for-update`
- **상태**: 측정 완료 — 졸업 조건 2/2 충족 (2026-08-17). 해석(섹션 2 비용 해석·3·4) 작성 중
- **동기 (Phase 0 결과)**: `findStock()` 의 SELECT 가 락을 잡지 않아 `if (stock < quantity)` 판단과 `decrease()` 차감이 서로 다른 시점의 재고를 봤다. 차감 자체는 원자적이었고(판매 125 = 재고 감소 125), 뚫린 것은 판단뿐이다 → oversold 19 = 재고 −19. ([phase-0.md](./phase-0.md) 섹션 2)
- **구현 정책**: 진단된 지점만 막는 최소 변화 — `findStock()` 의 SELECT 에 행 잠금(`FOR UPDATE`)을 걸어 판단→차감이 같은 트랜잭션의 같은 재고 위에서 이뤄지게 한다. 서비스 흐름·스키마는 Phase 0 그대로 (변화 지점 1곳 → 측정 비교가 깨끗해야 함).
- **보류한 후보**: 조건부 UPDATE(`WHERE stock_qty >= ?`, 갱신 행 수로 판정), 낙관적 잠금(version 컬럼). flash-sale 에는 조건부 UPDATE 가 더 단순·빠르지만, 비관적 락의 비용을 먼저 측정으로 확인한 뒤 이후 phase 에서 옮기며 차이를 재기 위해 지금은 택하지 않는다.

### 보조 관측 — 지연이 어디서 생기는가 (2차 실행, 내부 샘플링 동반)

졸업 판정은 1차 실행 기준이며, 이 실행은 비용의 위치를 가르기 위한 보조 자료다. 같은 조건(`RESET_STOCK=106`)으로 `load-test/sample-internals.sh` 를 배경에 띄우고 재실행: 34,668 req / ≈1,152 rps / p95 268ms (1차와 일치 — 샘플러 부하는 무시할 수준). 원본: [`internals-2026-08-17-run2.csv`](./phase-1-artifacts/internals-2026-08-17-run2.csv), [`k6-summary-2026-08-17-run2.json`](./phase-1-artifacts/k6-summary-2026-08-17-run2.json).

앱 풀(HikariCP, 최대 20)과 DB(`pg_stat_activity`) 를 약 2초 간격으로 함께 찍은 값 (부하 구간만):

> **표 읽는 법.** 요청 하나는 ① 풀에서 커넥션 획득 → ② `SELECT … FOR UPDATE` 로 행 락 획득 → ③ 판단·차감·INSERT·커밋(이 동안 커넥션과 락을 계속 보유) 순으로 지나가며, 기다리는 자리는 ①과 ② 뿐이다.
> - 풀 active = 커넥션을 물고 있는 요청 수(최대 20, 20/20 이면 풀 포화) · 풀 pending = ①에서 줄 선 요청 수 · 획득 평균 = ①에서 기다린 시간
> - DB active = DB 안에서 뭔가 하는 세션 · 그중 행 락 대기 = ②에서 멈춘 세션 · idle in tx = 트랜잭션은 열려 있으나 DB 는 노는 세션(앱 쪽 ③ 진행 중)
> - 대략 풀 active ≈ DB active + idle in tx. 읽는 순서: 락 대기가 0 인가 → 그때 풀이 20/20 인가 → pending·획득 평균이 얼마나 커졌나. 셋이 같이 움직이면 "락 → 풀 포화 → 대기" 사슬.

|---|---|---|---|---|---|---|
| 1 | – | – | – | 17 | 16 | 0 |
| 2 | 20/20 | 20 | 27ms | 20 | 19 | 0 |
| 3 | 3 | 0 | 41ms | 5 | 5 | 0 |
| 4 | 8 | 0 | 1ms | 19 | 18 | 0 |

| 6 | 20/20 | 95 | 83ms | 18 | 18 | 1 |

함께 뽑은 사실:

- 성공 주문 106건의 `created_at` 은 **2.87초** 안에 몰려 있다 (첫 주문 14:47:52.098 → 마지막 14:47:54.967, 주문 간 평균 27ms). 재고 소진은 부하 시작 직후 끝났다.
- 그런데 행 락 대기(DB 세션 15~19개)와 풀 포화(20/20, 대기 스레드 95~283)는 **30초 부하 내내** 이어졌다. `findStock()` 의 `FOR UPDATE` 는 재고 검사보다 먼저 실행되므로, 재고 0 이후의 거절 요청도 락을 잡은 뒤에야 거절된다.
- 유휴 상태에서 읽은 누계: 커넥션 획득 대기 총 3,672초 / 32,372회 (1차 실행분) → 요청당 평균 약 113ms 를 풀에서 기다림. 1차 실행 중앙값 132ms 의 대부분에 해당.
- 5xx 는 0 — 락 대기·풀 대기 모두 타임아웃 없이 지연으로만 흡수됨 (Hikari 기본 `connection-timeout` 30s 안쪽).

#### 대조군 — Phase 0 코드(락 없음)에 같은 샘플러를 붙인 실행

"락 대기가 없었을 때도 풀 대기가 생기는가"를 추론이 아니라 측정으로 답하기 위해, `phase-0/baseline-no-locking` 빌드를 같은 조건(`RESET_STOCK=106`, 워밍업 1회 후)으로 재실행: 57,930 req / ≈1,927 rps / p95 93ms, oversold 19 / 재고 −19 재현. 원본: [`internals-2026-08-17-phase0-control.csv`](./phase-1-artifacts/internals-2026-08-17-phase0-control.csv), [`k6-summary-2026-08-17-phase0-control.json`](./phase-1-artifacts/k6-summary-2026-08-17-phase0-control.json).

두 실행을 나란히 놓으면:

| | Phase 0 코드 (락 없음) | Phase 1 코드 (`FOR UPDATE`) |
|---|---|---|
| DB 행 락 대기 세션 | 소진 순간(≈2.8s)에만 16, 이후 **0** | **15~19 가 30초 내내** |
| 풀 pending 최대 | 88 (VU 300~500 구간에서만) | 283 (초반부터 지속) |
| 커넥션 획득 평균 | 0~26ms | 55~226ms |
| 풀 포화(20/20) | 간헐 | 지속 |
| idle in tx | 최대 17 (VU 피크) | 최대 5 |
| rps / p95 | 1,927 / 93ms | 1,152 / 268ms |

(참고: 락 없는 코드에서도 소진 순간에 락 대기 16이 찍힌 것은 `UPDATE … SET stock_qty = stock_qty - ?` 자체가 행 락을 잡기 때문 — 20개 커넥션의 UPDATE 가 잠깐 줄을 선다. 이 락은 UPDATE 한 문장 동안만 유지되므로 곧 사라진다.)
